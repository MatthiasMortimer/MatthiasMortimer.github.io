# Ecosystem Guide

## Architecture

This repository is an Astro multi-site workspace. `ritesGlobal/sites.registry.mjs` discovers every `sites/s-*` directory with a `site.meta.json`. Each site's `basePath` determines where `scripts/sync-sites.mjs` symlinks its `pages/` directory into generated `src/pages/` before `npm run dev` and `npm run build`.

Current sites:

| Site | Source | Route |
| --- | --- | --- |
| RitesDev | `sites/s-ritesdev/` | `/` |
| Blog | `sites/s-blog/` | `/blog` |

Do not edit `src/pages/` directly; it is generated by the sync script.

## Navigation And Synced Sites

Both sites render `ritesGlobal/components/SiteSwitcher.astro`. It reads the site registry at build time, marks the current site from `Astro.url.pathname`, and supports click-away and `Escape` dismissal. Site-local `SiteNav.astro` components own their local links; add a site's metadata and pages rather than hand-editing the switcher.

To add a site:

1. Create `sites/s-<name>/site.meta.json` with `slug`, `label`, `basePath`, and `order`.
2. Add a `pages/` directory.
3. Run `npm run sync` or either normal dev/build command.

## Global Content

`ritesGlobal/contact.json` is the source of truth for shared identity, contact details, social links, the primary logo, and avatar. `ritesGlobal/content.js` exposes that identity and a media map. Site-specific names, navigation, metadata, and labels live in each site's `content/site.json`.

Shared static assets are under `public/media/`. Add a new globally used media path to `ritesGlobal/content.js`; the Blog navigation demonstrates this with `media.blogLogo`.

Use the `globalContent` export when a page needs more than identity or media:

```js
import { globalContent } from "../../../ritesGlobal/content.js";

const { identity, media, projects, versions, sites } = globalContent;
```

It contains shared identity/contact data, media paths, projects, version data, and discovered site metadata. Keep site-specific copy in the site directory instead of creating another global registry.

`ritesGlobal/styles/tokens.css` defines shared colors, fonts, radii, shadows, and transitions. Each site imports it from its local `styles/global.css` and sets only local presentation values such as content width. `ritesGlobal/content-inventory.mjs` exposes `GLOBAL_CONTENT_FILES` and `getGlobalContentInventory()` for management tooling.

Management utilities resolve configured files by complete path or basename. For example, `getContentFilePath("ritesdev", "config", "site.json")` resolves to `sites/s-ritesdev/content/site.json`. Use this resolver rather than joining site paths manually. `writeContentFile()` creates a `.bak` backup by default, and `isPathSafe()` rejects paths outside the requested directory.

## Markdown And MDX Content

Every site stores editable data beneath its own `content/` directory. `content/site.json` contains reusable site settings, `content/pages/*.md` contains route copy and card content, and other JSON files contain reusable collections. The editor recursively discovers these files without a site-specific registry. Shared identity remains in `ritesGlobal/contact.json`.

Blog posts are MDX files under `sites/s-blog/content/posts/` and are rendered by the dynamic `pages/posts/[slug].astro` route. Example frontmatter fields are `title`, `pubDate`, `description`, `author`, `image`, and `tags`. Add the corresponding card entry to `sites/s-blog/content/posts.json` with a `/blog/posts/<slug>/` URL and a valid ISO date. The blog listing derives its tag filters from that structured JSON.

Minimal MDX example:

```mdx
---
title: "A useful debugging note"
pubDate: 2026-09-19
description: "What failed, why it failed, and the small fix."
author: "Matt"
tags: ["javascript", "debugging"]
---

## The failure

Describe the reproducible behavior, then document the verification.
```

The RitesDev contact form (`sites/s-ritesdev/components/ContactForm.astro`) submits JSON to `POST /api/inquiry`, which validates the fields, rejects honeypot submissions, and appends the entry through `ritesGlobal/inquiry-store.mjs` to the gitignored `dev/contact-submissions.jsonl`; the page shows an inline success/error banner. JSON is used because Astro's `security.checkOrigin` rejects form-encoded POSTs without a matching `Origin` header (which happens behind the Cloudflare tunnel). The same-route form POST in `contact.astro` remains as a no-JavaScript fallback. Saved inquiries are reviewed in the Inquiry Manager app; no email is sent.

## Dev Apps

Each app is self-describing through `devApps/<app>/devapp.meta.json`. RitesDev App scans those metadata files at runtime, so deleted folders disappear automatically. The management CLI uses `ritesGlobal/devapps-registry.mjs`; keep it aligned when adding an app.

Apps that ship a `devapp.api.mjs` (exporting `createApiHandler()`) and a `public/index.html` are **embedded**: RitesDev App serves them at `/apps/<folder>/` inside its own process and shows them as tabs, so nothing extra has to boot when you switch between them. They have no Electron entry point of their own and cannot be launched separately. Set `"embed": false` in the metadata for apps that must stay standalone (Site Hosting manages long-running processes, so it stays a separate window). `"tabOrder"` controls tab position.

| App | Folder | How to open | Purpose |
| --- | --- | --- | --- |
| Website Content Editor | `devApps/content-editor` | tab in RitesDev App | Edit site copy, data, and Markdown |
| Blog Post Manager | `devApps/blog-post-manager` | tab in RitesDev App | Create/manage blog MDX posts |
| Inquiry Manager | `devApps/inquiry-manager` | tab in RitesDev App | Triage contact form inquiries |
| RitesDev App | `devApps/ritesDevApp` | `npm run app` | Master window: hosts app tabs, controls Site Hosting |
| Site Hosting | `devApps/siteHosting` | `npm --prefix devApps/siteHosting start` | Control local Astro hosting and Cloudflare tunnel |

Management commands: `npm run mgmt:status`, `npm run mgmt:apps`, `npm run mgmt:content`, and `npm run mgmt:setup`. Run `bash devApps/install-all-launchers.sh` after renaming or adding apps to refresh the desktop menu entries.

To add an app, create its folder, `package.json`, `devapp.meta.json`, `public/index.html`, and `devapp.api.mjs`; it then appears as a tab automatically. Add the matching entry to `ritesGlobal/devapps-registry.mjs` until the management registry is fully metadata-driven. Keep the slug, `manages`, and `contentTypes` values aligned. Run `npm run mgmt:setup` and `npm run mgmt:apps` before launching it.

## Dependencies

Root runtime dependencies: Astro 7.3.2, `@astrojs/mdx` 8.0.1, `@astrojs/node` 11.1.6, and `@astrojs/cloudflare` 14.3.2. Node 22.12 or later is required; validation used Node 22.23.1 and npm 10.9.8.

The Blog Post Manager depends on `gray-matter` and Electron. The Launcher depends on Express and Electron. Site Hosting uses Electron. `npm ls --depth=0` currently reports several extraneous transitive WASM/sharp packages; run `npm install` after dependency changes to reconcile the lockfile and installed tree.

## Validation And Known Boundary

The verified checks are `npm run build`, `npm run mgmt:setup`, `npm run mgmt:status`, and `npm --prefix devApps/blog-post-manager test`. Browser smoke testing covered all public routes, the contact form's required fields, and SiteSwitcher open/Escape-close behavior.

`ritesGlobal/content-management.mjs` is a legacy helper that parses JavaScript post registries with `eval`; it is not used by the tested Blog Post Manager workflow. Replace that parser with a structured JSON or MDX metadata store before exposing it to untrusted content.
